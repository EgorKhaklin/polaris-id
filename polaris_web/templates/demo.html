A token's life, four steps.

Polaris is the anti-coercion identity substrate. The deepest constraint, deeper than C1 to C10, is that no person be compellable into renouncing, transferring, or surrendering their identity against their will. The four steps below follow one token through that lens. The procedures, triggers and constraints named are the ones this repository ships and its tests exercise; the data is synthetic. Step 1

Issue

An authorized agency issues an identity token for an individual. uc1_issue_and_activate is the single-shot path that creates the Individual + IdentityToken + first TokenLifecycleEvent in one atomic transaction. The post-quantum algorithm is bound by reference, not hardcoded.

Procedure

SELECT uc1_issue_and_activate(
    p_legal_name             := 'Maria Santos',
    p_dob                    := '1992-03-14',
    p_jurisdiction           := 'US-PA',
    p_issuing_agency_id      := 1,    -- US National Identity Service
    p_algorithm_id           := 1,    -- ML-DSA-65 (post-quantum)
    p_biometric_binding_type := 'FINGERPRINT',
    p_witness_agency_id      := 2,
    p_liveness_check_type    := 'MULTI_MODAL',
    p_token_value            := 'PSV-2026-MS-0007',
    p_physical_serial        := 'NTS-AX44-019',
    p_hardware_model         := 'NeoSecure GX-2',
    p_permitted_contexts     := ARRAY[1, 3, 5]
) AS new_token_id;

Effect

  • Inserts Individual + IdentityToken rows atomically
  • Token status: ACTIVE on first issuance, with its first signature row written in the same transaction
  • Trigger appends TokenLifecycleEvent { event_type: 'ISSUED' }
  • A foreign key to CryptographicAlgorithm: the algorithm rotates by row update, not by redeploy
  • TokenPermission rows created for each permitted VerificationContext

What's enforced

C7, no hardcoded cryptography. The token references algorithm_id = 1; the operator chose post-quantum ML-DSA-65 at issuance. Rotating to ML-DSA-87 or SLH-DSA is a row update in CryptographicAlgorithm, not a redeploy.

C1, issuance is recorded permanently. The lifecycle row cannot be updated or deleted after commit; the append-only trigger refuses. The audit of record is constitutional.

Step 2

Activate (successor)

A holder loses their token and a successor must take its place. uc4_activate_reserve is the two-stage path: a RESERVE successor token already exists, issued ahead of time; this call atomically marks the lost token LOST and flips the reserve to ACTIVE. Optionally, enroll a duress code on the new token.

Procedure

SELECT uc4_activate_reserve(
    p_lost_token_id      := 27,
    p_actor_agency_id    := 1,
    p_reason_code        := 'LOST_IN_TRANSIT',
    p_reserve_token_id   := 42,
    p_published_location := 'CRL/2026-05-15/CA-12'
) AS activated_token_id;

-- Optional: enroll a duress code on the new token.
UPDATE IdentityToken
   SET duress_code_hash = ('scrypt:32768:8:1$' || …)
 WHERE token_id = 42;

Effect

  • Lost token transitions ACTIVE → LOST (terminal; lifecycle event appended)
  • Reserve token transitions RESERVE → ACTIVE (lifecycle event appended)
  • Partial unique index uq_one_active_per_person attempts the insert atomically
  • RevocationList row appended for the lost token (CRL pointer)
  • If a duress code is enrolled: duress_code_hash is set, and verifications compare against it in constant time

What's enforced

C3, one ACTIVE token per individual. The partial unique index keys on (individual_id) WHERE status = 'ACTIVE'. Two operators racing successor activation: one commits, the other gets a 23505 unique-violation.

The duress code. When set, the verification flow compares the holder's typed code against this hash in constant time. A match silently records a DuressEvent while the user-visible verification proceeds exactly as it otherwise would: the secret name that signals coercion without revealing the signal.

Step 3

Verify

A relying agency checks the token. Three disclosure levels available: FULL (full identity reveal), SELECTIVE (named attributes only), ZERO_KNOWLEDGE (proves a valid token exists, reveals nothing else). Two audit surfaces sit on this step: an operator-supplied requesting_purpose_text on each verification, and a meta-audit table recording who read the audit trail afterwards.

Procedure (FULL, with purpose)

INSERT INTO VerificationEvent (
    token_id,
    requesting_agency_id,
    context_id,
    outcome,
    disclosure_level,
    requestor_location,
    requesting_purpose_text
) VALUES (
    42,
    4,    -- Transportation Security Admin
    3,    -- TRAVEL context
    'SUCCESS',
    'FULL',
    'JFK Terminal 4, gate B22',
    'border crossing, random check'
);

Procedure (ZERO_KNOWLEDGE)

INSERT INTO VerificationEvent (
    token_id,            -- MUST be NULL for ZK (C2)
    requesting_agency_id,
    context_id,
    outcome,
    disclosure_level,
    proof_commitment
) VALUES (
    NULL,
    4, 3, 'SUCCESS', 'ZERO_KNOWLEDGE',
    '0x' || encode(sha256_zk_proof, 'hex')
);

Effect

  • VerificationEvent row inserted (append-only by trigger)
  • FULL: token_id populated; full identity revealed via JOIN
  • SELECTIVE: token_id populated; permitted attributes only
  • ZK: token_id IS NULL; identity not derivable from the event
  • Federation gate: the verifier must hold an active AgencyTrustAttestation toward the issuing agency for this context
  • The requesting_purpose_text is recorded permanently, so a coerced verification leaves the coercer's stated context in the audit chain
  • Meta-audit: any later read of this row by an authorized operator is logged in AuditAccessLog with who read it, when, and under what filter

What's enforced

C2, zero-knowledge events cannot reveal identity. A CHECK constraint on the row refuses any ZERO_KNOWLEDGE event that carries a token_id, whoever writes it and through whichever client.

The federation gate. A SUCCESS outcome requires an active trust attestation from the verifying agency toward the issuing agency for this context. Cross-jurisdictional trust is recorded, never assumed.

Purpose and meta-audit. The first records why each verification happened, in the requester's own words; the second records who read the audit trail afterwards. The audit's audit.

Step 4

Revoke

The token is revoked: compromised, lost, or superseded. The row stays in the database with terminal status; the data is never erased. uc8_revoke_token applies the state transition + appends the lifecycle event + writes a RevocationList pointer. The issuer-discretion policy fires if the agency's recent revocation rate exceeds its declared bound.

Procedure

CALL uc8_revoke_token(
    p_token_id           := 42,
    p_actor_agency_id    := 1,
    p_reason_code        := 'COMPROMISED',
    p_published_location := 'CRL/2026-05-15/CA-12',
    p_cosigner_agency_id := NULL    -- optional dual-sign
);

Effect

  • Status transitions ACTIVE → REVOKED (legal edge per state-machine trigger)
  • Lifecycle row REVOKED appended with reason
  • RevocationList row appended (CRL pointer published)
  • The revocation-velocity trigger samples the agency's recent rate and refuses a burst above its policy bound without a co-signer
  • The row stays: non-repudiation requires the historical record

What's enforced

C1, revocation is recorded, not erased. The lifecycle event is append-only; the IdentityToken row survives with terminal status. An operator cannot tidy up a holder's history.

Issuer discretion. A burst of revocations from one agency is refused above its declared bound unless a second agency co-signs. The schema names the abuse vector so governance can catch it.

What you just saw

Four procedures called. Four rows appended to audit tables. Constraints enforced at the database layer: C1, C2, C3 and C7, plus the federation gate, the duress code and the issuer-discretion bound. The application code gets no opportunity to violate them quietly.

The walkthrough is synthetic, but the procedures, triggers, and constraints are not. They live in polaris_sql/05_procedures.sql + 06_triggers.sql; the corresponding schema lives in polaris_sql/01_schema.sql; the test suite (the DB-backed product suites, the SQL self-tests, the Hypothesis property tests, and the polaris_checks invariant layer) runs them every release. The data model is documented at docs/reference/DATA-MODEL.md in the repository.

The anti-coercion vocation Polaris serves runs through every step: post-quantum crypto (C7) protects against future cryptanalytic coercion; append-only audit (C1) prevents silent rewriting of history; one-ACTIVE-per-individual (C3) prevents identity duplication attacks; ZK disclosure (C2) prevents downstream surveillance; duress codes give holders a silent signal under physical coercion; the stated purpose on each verification records the coercer's own account of it; and the meta-audit records who read the trail afterwards. Each is necessary; none alone is sufficient.
