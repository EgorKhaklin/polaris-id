Step 1: Issue

An authority issues a credential to a person. uc1_issue_and_activate checks that the authority may issue under the chosen algorithm, then writes the person, the credential, its first signature and its lifecycle events in one transaction.

Procedure

SELECT uc1_issue_and_activate(
    p_legal_name             := 'Maria Santos',
    p_dob                    := '1992-03-14',
    p_jurisdiction           := 'US-PA',
    p_issuing_agency_id      := 1,
    p_algorithm_id           := 1,   -- ML-DSA-65
    p_biometric_binding_type := 'FINGERPRINT',
    p_witness_agency_id      := 2,
    p_liveness_check_type    := 'MULTI_MODAL',
    p_token_value            := 'PSV-2026-MS-0007',
    p_physical_serial        := 'NTS-AX44-019',
    p_hardware_model         := 'NeoSecure GX-2',
    p_permitted_contexts     := ARRAY[1, 3, 5],
    p_signature_bytes        := $1   -- signed by the app
) AS new_token_id;

What it writes

  • An Individual row and an IdentityToken row
  • A TokenSignature row in the same transaction: the signature the application's signing module made
  • Two lifecycle events, ISSUED and the activation, the second written by a trigger on the status change
  • A TokenPermission row for each context the credential may be verified in

What holds it

C7, the algorithm is data.Schema The credential names algorithm_id = 1, a row in CryptographicAlgorithm, and the procedure refuses an algorithm the authority is not authorized for or one already deprecated. Moving credentials to another algorithm is uc6_migrate_algorithm, a path that runs; the signers a verifier accepts are a short list in code, by design. The claim is algorithm agility under an audited migration path, not settled security against a quantum adversary; what a break would cost is in the readiness ledger.

C1, issuance is recorded for good.Schema A trigger refuses any update or delete of a lifecycle event, whoever connects.

Step 2: Activate a reserve

The holder reports the credential lost, and a reserve credential issued ahead of time takes its place. uc4_activate_reserve marks the lost one LOST and moves the reserve to ACTIVE in one transaction.

Procedure

SELECT uc4_activate_reserve(
    p_lost_token_id      := 27,
    p_actor_agency_id    := 1,
    p_reason_code        := 'LOST_IN_TRANSIT',
    p_reserve_token_id   := 42,
    p_published_location := 'CRL/2026-05-15/CA-12'
) AS activated_token_id;

-- A duress code is enrolled by the database owner.
-- The application role is refused this write.
UPDATE IdentityToken
   SET duress_code_hash = 'scrypt:32768:8:1$…'
 WHERE token_id = 42;

What it writes

  • The lost credential moves ACTIVE → LOST, a terminal state, with its lifecycle event
  • The reserve moves RESERVE → ACTIVE, with its lifecycle event
  • A RevocationList row for the lost credential
  • If the holder wants a duress code, the owner enrols it: only its scrypt hash is stored, never the code

What holds it

C3, one active credential per person.Schema A partial unique index on (individual_id) WHERE status = 'ACTIVE' refuses a second, whichever path tries to create it and however many operators race. The index keys on the person record: two records for one person are a question for enrolment, which this index does not answer.

The duress code.Application A holder who gives their duress code at a verification sees it proceed exactly as it otherwise would, while a DuressEvent is recorded off the request thread, so the response time does not tell. It helps against a coercer who does not know the mechanism exists, not against one who does, and the record it appends cannot be removed (the duress assessment).

The holder's binding.Schema Outside the issuance and recovery procedures, a trigger lets the application change a credential's status and nothing else: not its holder, issuer, value, expiry or duress code.

Step 3: Verify

A relying authority checks the credential at one of three disclosure levels: FULL (the credential and its holder), SELECTIVE (named attributes only) or ZERO_KNOWLEDGE (a proof that a valid credential exists, naming none). A verification can carry the requester's stated purpose, and an operator's later read of the log is itself logged.

Procedure: full disclosure, with a purpose

INSERT INTO VerificationEvent (
    token_id,
    requesting_agency_id,
    context_id,
    outcome,
    disclosure_level,
    requestor_location,
    requesting_purpose_text
) VALUES (
    42,
    4,   -- the verifying authority
    3,   -- the TRAVEL context
    'SUCCESS',
    'FULL',
    'JFK Terminal 4, gate B22',
    'border crossing, random check'
);

Procedure: zero knowledge

INSERT INTO VerificationEvent (
    token_id,   -- must be NULL (C2)
    requesting_agency_id,
    context_id,
    outcome,
    disclosure_level,
    proof_commitment
) VALUES (
    NULL,
    4, 3, 'SUCCESS', 'ZERO_KNOWLEDGE',
    '0x' || encode(proof_digest, 'hex')
);

What it writes

  • A VerificationEvent row, append-only by trigger
  • FULL and SELECTIVE name the credential (token_id); ZERO_KNOWLEDGE names none
  • The requester's stated purpose, when one is given, kept with the event for good: a coerced verification keeps the coercer's own account of it
  • Each later read of the log by an operator: an AuditAccessLog row saying who read it, when, and under which filter

What holds it

C2, a zero-knowledge event names no credential.Schema A CHECK constraint refuses a ZERO_KNOWLEDGE row that carries a token_id, whoever writes it. It bounds what the log stores; a verifier shown a full credential still sees its stable token value, so correlation across verifiers is bounded, not eliminated.

The federation gate.Application The console refuses to record a SUCCESS unless the verifying authority holds an active trust attestation toward the issuing authority for this context. Trust is one recorded hop, never transitive.

The meta-audit.Application The stated purpose records why a verification happened; the access log records who read the trail afterwards.

Step 4: Revoke

The credential is revoked: compromised, lost or superseded. uc8_revoke_token moves it to REVOKED, appends the lifecycle event and the revocation-list row, and holds the issuing authority to its revocation bound. The row stays.

Procedure

CALL uc8_revoke_token(
    p_token_id           := 42,
    p_actor_agency_id    := 1,
    p_reason_code        := 'COMPROMISED',
    p_published_location := 'CRL/2026-05-15/CA-12',
    p_cosigner_agency_id := NULL   -- or a co-signer
);

What it writes

  • The credential moves ACTIVE → REVOKED, an edge the state-machine trigger allows
  • A REVOKED lifecycle event with its reason
  • A RevocationList row pointing at the published list
  • Nothing is deleted: the credential row stays, with its terminal status

What holds it

C1, revocation is recorded, not erased.Schema The lifecycle event is append-only, and the credential row survives with its terminal status. An operator cannot tidy up a holder's history.

The issuer-discretion bound.Schema The procedure refuses a revocation that would take an authority above its declared rate unless a second authority co-signs, and a trigger refuses any move to REVOKED that does not come through the procedure.

What you just saw

Four procedures and the rows they append. The rules marked Schema hold whoever connects: the append-only triggers (C1), the zero-knowledge CHECK (C2), the one-active index (C3), the algorithm as a row (C7), the binding trigger and the issuer-discretion bound. The rules marked Application hold while the application is honest: the federation gate, the duress comparison and the meta-audit.

The data here is synthetic. The procedures live in polaris_sql/05_procedures.sql, the triggers in 06_triggers.sql and the schema in 01_schema.sql, and the test suites exercise them on every change. The tables are described in DATA-MODEL.md, and what is and is not ready in PRODUCTION-READINESS.md.

Each rule answers one abuse: a rewritten history, a zero-knowledge record that names its credential, a second active credential, an algorithm that cannot be replaced, a burst of revocations from one authority, a verifier trusting without a record. They serve the vocation that no person be compellable into renouncing, transferring or surrendering their identity; none of them prevents compulsion by itself.
