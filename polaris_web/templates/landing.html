What the schema enforces

Ten hard constraints (C1–C10) are not policies. They are triggers, CHECK constraints, partial unique indexes, and append-only audit trails. The system cannot be operated in a way that violates them.

C1

Audit of record

Every state change of an identity token writes a TokenLifecycleEvent row. Every verification writes a VerificationEvent. Both tables are append-only at the trigger level. Nine schema tables are append-only audit-of-record instances, each enforced by a trigger.

C2

Zero knowledge

Verifications at the ZERO_KNOWLEDGE disclosure level have token_id IS NULL, enforced by a CHECK constraint on the row and by form coercion before it. The verification graph cannot be reconstructed from ZK events. A real Plonky2 ZK-SNARK proves membership without revealing which token.

C3

One identity per person

A partial unique index makes a second ACTIVE token for the same individual a database-level error. Concurrent writes lose the race deterministically.

C10

Identity is not money

The schema has no transactions, balances, spending patterns, or merchant codes. Adding any of those would require a constitutional amendment that the project refuses on sight. If a value system is ever built on top, it lives in a separate database whose foreign keys prove the separation rather than merely claim it.

Six more constraints round out C1-C10: C4 atomic failed-login counters (no TOCTOU race); C5 CSP forbids inline scripts (no script-src 'unsafe-inline'); C6 server-side disclosure enforcement (client cannot upgrade ZK to FULL); C7 no hardcoded cryptography (algorithm references the CryptographicAlgorithm table; rotation is a row update); C8 bounded result sets on all /api/atlas/* endpoints (no unbounded query exhaust); C9 concurrency hazards tested with real threading, not mocks. The four cards above are the highlight reel for first-time visitors; the canonical text for all ten lives in MISSION.md, "The hard constraints". Anti-coercion is the vocation all ten constraints serve, stated in MISSION.md, "Vocation", above C1 to C10.

Built on real cryptography

ML-DSA-65

NIST FIPS 204 lattice signatures on every token, real under the production default and a labelled deterministic placeholder otherwise. The full posture, including what is still classical, is in PQC-POSTURE.md.

Plonky2 ZK-SNARK

FRI-based, transparent setup, hash-only commitments. Proves epoch membership without revealing which token.

Merkle anchoring

SHA3-256 Merkle commitments over batched anchor sets. Per-leaf inclusion proof is logarithmic in batch size.

Multi-sig migration

M-of-N signature schemes per token. Algorithm rotation without invalidating existing tokens.

Duress codes

Constant-time comparison. Coercer-visible flow is identical to the legitimate one. DuressEvent row appears in the audit table.

Federation

Per-context trust attestations. Agency V accepts agency I for context C until date D. No transitive trust.

Guarantees you can check, not take on faith

Every constitutional constraint is enforced where application code cannot bypass it: database triggers, partial unique indexes, and CHECK constraints. On top of the schema, a flat check layer re-verifies each constraint on every run, and its ability to catch a violation is itself tested against broken fixtures.

  • Schema-level enforcement: C1-C10 live in the database, not in policy. A reviewer can read the triggers and indexes and see each guarantee directly.
  • polaris_checks: a flat layer of plain check functions: one per constitutional constraint plus production-posture pins, each provably able to catch its violation, gating CI on every run.
  • Independent second witness: the zero-knowledge epoch root is recomputed by a separate Python implementation and checked bit-for-bit against the Rust prover. No single implementation is trusted alone.
  • Append-only audit-of-record: every state change leaves a row the system can reconstruct; UPDATE and DELETE are rejected by trigger.

Deploying the stack

The deployment path ships in the repository and is scripted end to end. Polaris is pre-pilot: it is not yet a system you can run with real identity data, and what still stands between here and there is listed openly in PRODUCTION-READINESS.md. 

git clone <polaris repo> && cd polaris
./scripts/polaris-generate-secrets.sh
export POLARIS_DOMAIN=polaris.example.com
./scripts/polaris-deploy.sh prod
curl -fsS https://${POLARIS_DOMAIN}/api/health | jq .

Within ~90 seconds: Caddy provisions Let's Encrypt TLS, Postgres + Redis + gunicorn come up, /api/health returns structured per-component status. The operator runbook is OPERATIONS.md; the secrets primer is SECRETS.md, and what a deployment still needs from its operator is PRODUCTION-READINESS.md.
