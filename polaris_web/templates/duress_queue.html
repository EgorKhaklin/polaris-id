How duress detection works

Each IdentityToken may optionally carry a Werkzeug scrypt hash of a secondary "duress" code. During verification, the operator's terminal accepts a "Holder verification code (optional)" input. When the holder enters their duress code under coercion:

  1. Constant-time comparison: the input is compared against the stored hash in constant time, so a coercer timing the response learns nothing.
  2. Identical observable behaviour: the verification proceeds with whatever outcome the operator recorded; the coercer-visible response is the same with or without the signal.
  3. Audit of record: a row appears in this table. DuressEvent is append-only by trigger.
  4. Anti-revealing: the operator-visible verification list never joins to DuressEvent; only this page and the admin and auditor roles see it.

Every new row increments polaris_duress_events_total, which fires the PolarisDuressEvent alert immediately and pages the on-call responder; the response runbook is docs/operator/RUNBOOKS.md.
